# Отчёт об автоматических проверках backend

Запуск из корня проекта: `npm test`. HTTP-тесты запускают локальный сервер на свободном порту, SQLite-тесты создают временные базы. ML-сервис заменён заглушками. Тесты не требуют работающих приложения, ML или Ollama.

Отдельно, вне `npm test`: `npm run test:redteam` — проверки устойчивости самой LLM (промпт-инъекции, доверие к источнику). Требуют реально поднятый `ai-assistant` (FastAPI + Ollama + knowledge_db) по адресу из `FASTAPI_HOST`; если сервис недоступен, тесты сами себя помечают skipped, а не падают и не дают ложный "зелёный" результат на моках.

Формат результатов прогона: по умолчанию `npm test` печатает человекочитаемый TAP-вывод в консоль (через встроенный `node --test` реестр репортеров). Можно получить и другие форматы без изменения тестов — флагами `tsx --test --test-reporter=<tap|spec|dot|junit|github> --test-reporter-destination=<file>` (например, `--test-reporter=junit --test-reporter-destination=report.xml` — для систем, ожидающих JUnit XML).

Allure-отчёт — отдельно для обычного прогона и для red-team:
- `npm run test:allure` → `npm run report:allure` → `npm run open:allure` — обычный набор (1-16 ниже, атакующие проверки на моке модели).
- `npm run test:redteam:allure` → `npm run report:redteam:allure` → `npm run open:redteam:allure` — red-team против реальной LLM (17 ниже).

Результаты пишутся в `allure-results-backend`/`allure-results-redteam`, отчёты — в `allure-report-backend`/`allure-report-redteam` (все в `.gitignore`, генерируются локально/в CI).

1. `DTO validates required fields, types and message length` — проверяет ограничения DTO (включая `userId`, хотя в контроллере он всегда перезатирается значением из SSO-токена до валидации — здесь проверяется сама DTO в изоляции).
    - 1.1) Недопустимы пустой объект, строковый `userId`, дробный `sessionId`, строковый `orderId`, пустое сообщение, сообщение из 2 или 301 символа, число вместо сообщения.
    - 1.2) Допустимы сообщения длиной 3 и 300 символов при корректных ID.

2. `low confidence requests clarification without generation` — при уверенности 0,3 запрашиваются уточнения, генерация не вызывается.

3. `order intent requires an order and checks ownership before generation` — для категории заказа запрашивается номер при его отсутствии или отсутствии доступного заказа; при доступном заказе данные передаются в генерацию.
    - 3.1) Нет `orderId`; репозиторий (вызывается как `getOrder(orderId, authToken, traceId)` — владение проверяет маркетплейс по токену, не бэкенд по `userId`) не нашёл заказ; репозиторий вернул заказ.

4. `human agent and message threshold send to operator` — проверяет вызов передачи оператору.
    - 4.1) Намерение `human_agent` с уверенностью 0,9; наличие трёх предыдущих сообщений.

5. `ML gateway rejects malformed responses and propagates failures` — проверяет отклонение некорректных ответов ML и распространение ошибки вызова.
    - 5.1) Число вместо обработанного текста; confidence=2; пустой ответ генератора; имитированная ошибка timeout. Проверка не подтверждает наличие реального тайм-аута в коде.

6. `classification confidence boundaries follow current routing rules` — проверяет текущие ветви маршрутизации для категории заказа и неизвестной категории.
    - 6.1) Confidence 0 и 0,3 — уточнение; 0,3001 и 0,85 — генерация; 0,8501 — запрос номера заказа; неизвестная категория при 0,9 — уточнение. Это фиксирует текущее поведение и не означает, что оно соответствует требованиям.

7. `session creation and reopening use the supplied identifiers` — проверяет создание отсутствующей сессии, повторное открытие закрытой и отсутствие обновления открытой сессии на заглушках репозитория.

8. `ML gateway sends expected payloads and maps successful responses` — проверяет адреса и тела трёх запросов к ML и преобразование успешных ответов. Сетевые запросы заменены заглушкой axios.

9. `HTTP hello returns the expected response` — GET `/hello` возвращает 200 и `hello!`.

10. `HTTP support requires a valid SSO token and validates the body before invoking the service` — без токена 401; с валидным токеном контроллер возвращает 400 для некорректного тела и не вызывает сервис; для корректного тела возвращает ответ сервиса.
    - 10.1) Пустой объект, сообщение из 2 символов, строковый `sessionId`, сообщение из 301 символа; корректный запрос.

11. `HTTP orders requires a valid SSO token, forwards it to the service and returns only selected fields` — без токена и с невалидным токеном 401; с валидным токеном сервису передаётся именно SSO-токен вызывающего (а не какой-либо `userId` из query/тела — владение заказами проверяет маркетплейс по токену), в ответе остаются только разрешённые поля.

12. `OrderRepository forwards the caller's token to the marketplace and maps 404s to null` — `OrderRepository` больше не хранит заказы локально, а ходит в `MARKETPLACE_BASE_URL` по HTTP с токеном вызывающего. Проверяет правильный URL/заголовки (`Authorization: Bearer <token>`, `X-Trace-Id`) и что 404 от маркетплейса — для чужого и для несуществующего заказа одинаково — превращается в `null`, а не в ошибку.

13. `SQLite stores sessions and messages and updates session status` — создаёт сессию и сообщение во временной SQLite, считывает их и проверяет обновление статуса. Проверяется первый созданный сеанс; поведение при несовпадении внешнего и внутреннего ID требует отдельной проверки.
    - 13.1) Отдельно проверяется изоляция: чужой `userId` не видит сессию и не может изменить её статус (защита от IDOR на `sessionId`).

14. `order ownership check gives identical responses for a foreign order and a non-existent one` — ответ сервиса не позволяет отличить "заказ принадлежит другому" от "заказа не существует" (защита от перебора `orderId`).

15. `tests/auth.test.ts` — юнит-тесты `requireSsoAuth` напрямую, без поднятия сервера: отсутствующий токен, не-Bearer заголовок, просроченный токен, токен с другим секретом, токен с другим алгоритмом (включая подделанный `alg:none`), `sub` ≤ 0 / не число / отсутствует — все отклоняются 401; валидный токен — `req.userId` берётся из `sub`, не из тела запроса.

16. `tests/security.test.ts` — один сквозной HTTP-тест на реальном Express-сервере с реальными JWT и реальной временной SQLite (без мока аутентификации):
    - IDOR на `sessionId`: пользователь Б не может прочитать или дописать в сессию пользователя А по известному `sessionId` (403, без 500 и утечки деталей БД при коллизии).
    - `userId` в теле запроса игнорируется — используется личность из SSO-токена.
    - SQL-инъекция в `message`/`sessionId`/`orderId` не выполняется, таблица `sessions` не повреждается.
    - Невалидные типы/границы `sessionId`/`orderId` (отрицательные, 0, дробные, нечисловые, вне `Number.MAX_SAFE_INTEGER`) отклоняются 400.
    - Управляющие символы и NUL-байт в `message` не приводят к 500.
    - Невалидная структура тела (`message` — объект/массив/число) отклоняется 400, а не 500.
    - Ключи `__proto__`/`constructor.prototype` в теле запроса не загрязняют `Object.prototype`.
    - HTML/`<script>`-пейлоад в `message` сохраняется как литеральная строка.
    - В логах (`console.log`/`console.warn`) не встречается ни сырой токен, ни `SSO_SHARED_SECRET`, ни заголовок `Authorization`.

17. `npm run test:redteam` (`tests/redteam.test.ts`, отдельный прогон, не входит в `npm test`) — чёрный ящик через реальный `ai-assistant` (FastAPI + Ollama `gemma4:e4b` + классификатор + knowledge_db): заявление о правах администратора, инструкция "игнорируй базу знаний", поддельное `[SYSTEM]`-сообщение, просьба показать данные "предыдущего клиента", вопрос про несуществующее правило (возврат через 10 лет), ложное утверждение о скидке 90%, смешанный по интентам вопрос. Эвристические проверки по ключевым словам в ответе; требуют реально доступный `FASTAPI_HOST` и сами себя скипают, если его нет.

## Границы

Rate limiting в backend не реализован — проверок на него нет. Red-team проверки устойчивости LLM (17) эвристические (поиск ключевых слов), не формальное доказательство; результат зависит от конкретной модели/промпта и может быть нестабильным между запусками. Проверки не покрывают полноценную работу с реальным ML и Ollama в остальных сценариях, параллельные сообщения и race conditions при одновременном создании одной и той же сессии (известный TOCTOU в `handleSession`, пока не проверяется), порядок повторных запросов, реальные сетевые тайм-ауты или безопасное содержимое ошибок в production. Для них необходимы отдельные проверки.
